架构评审报告

知识库检索引擎 1.0.0 — 从架构师视角识别的 20 个待完善领域
评审版本: 1.0.0 日期: 2026-08-15 状态: 待定稿 评审范围: 并发模型 / 进程架构 / DSL 引擎 / 数据模型 / 部署拓扑

评审总览

前序架构在并发模型方面做出了正确的设计选择：进程分离、SKIP LOCKED 任务分发、租约+心跳、Fencing Token、幂等键——这些构成了一个健壮的并发基础设施。但架构设计文档的覆盖范围与深度仍存在显著缺口。

本次评审共识别出 20 个待完善领域，按严重程度分为四类：

严重 架构根本性缺陷，会导致生产事故 高 重要功能缺失，影响系统成熟度 中 设计不完备，增加技术债务 低 优化建议，后续迭代补齐

G1（API 契约）、G6（性能模型）、G9（DSL 语法）、G12（数据模型）这四个严重缺陷会直接影响代码实现的可交付性。建议在进入编码阶段前，先完成这些模块的设计。

G1
严重 P0

完整 API 契约缺失

文档中仅提及 POST /api/matches/analyze 一个端点，整个知识库系统的 API 面完全未定义。

  • 没有 API 版本化策略（/api/v1/ vs /api/v2/），前端与后端无法独立演进
  • 没有统一的错误响应格式（RFC 7807 Problem Details），客户端无法编程式处理错误
  • 没有分页、过滤、排序标准（cursor vs offset/limit），规则列表查询无法扩展
  • 没有 WebSocket / SSE 端点，实时推送（比赛分析完成、规则触发告警）无通道
  • 没有健康检查端点的详细规范（/api/health 的响应结构、状态码、依赖检查粒度）
G2
高 P0

数据治理模型缺失

前序设计定义了 trust_level 和 eligible 字段，但没有定义数据治理的完整机制。

  • 没有数据血缘（Lineage）追踪——证据记录依赖哪些源数据？推理链如何追溯？
  • 规则质量评分机制缺失——如何评估一条规则的预测准确率？如何自动淘汰低质量规则？
  • 规则衰减（Decay）策略缺失——基于历史数据的规则可能因赛季更新、球队变化而失效
  • 数据准入（Data Eligibility）标准不完整——eligible 字段仅是一个布尔值，判断逻辑未定义
  • 没有数据生命周期管理——历史证据记录何时归档？何时删除？
G3
高 P1

可观测性体系不完整

Section 10 提到了 Prometheus 和 Grafana 但仅作为可选组件，没有定义可观测性的具体内容。

  • 没有分布式追踪（Distributed Tracing）——一个分析请求跨越 API → 检索 Worker → DSL 引擎 → 证据记录，链路上出问题无法定位
  • 没有结构化日志规范——日志格式、级别、采样策略、敏感信息脱敏
  • 没有业务指标定义——规则命中率、预测准确率、分析延迟、证据记录率等关键业务指标缺失
  • 没有告警规则——Worker 心跳丢失、任务积压、租约过期率升高等场景无告警
  • 健康检查仅覆盖存活性和就绪性，缺少依赖深度检查（慢查询检测、连接池水位）
G4
高 P1

安全与权限模型缺失

文档提及"认证"，但安全模型远不止于认证——没有定义谁来管理规则、谁来发起分析、谁来审批。

  • 没有 RBAC 模型——规则创建者、审核者、审批者、管理员四个角色缺少权限矩阵
  • 没有 API 速率限制——恶意的分析请求可能耗尽 Worker 资源
  • 没有数据加密策略——证据快照包含敏感预测数据，传输和存储加密未定义
  • 没有审计日志的策略——谁在什么时候修改了规则、谁触发了回测、结果如何变更
  • 没有多租户隔离——如果多个用户或团队共享知识库，数据隔离怎么办？
G5
中 P1

失败模式与容错策略缺失

文档覆盖了 Worker 崩溃的场景（租约+Fencing Token），但系统还有更多失败模式未覆盖。

  • 没有 Circuit Breaker 模式——Redis 队列不可用时，API 是否应继续接受分析请求？
  • 没有 Bulkhead 隔离——回测作业消耗大量 CPU，是否会影响实时检索的延迟？
  • 没有降级策略——当 DSL 引擎不可用时，系统是否应该返回缓存的分析结果？
  • 没有重试风暴防护——大量任务同时失败时，重试是否会导致雪崩？
  • 没有数据库连接池溢出防护——多个 Worker 同时连接 PostgreSQL，连接池上限如何配置？
G6
严重 P0

性能模型与容量规划缺失

架构设计完全可以支撑并发，但没有任何量化指标来指导部署决策——需要多少 Worker？多少内存？

  • 没有预期吞吐量——单场比赛分析需要多少毫秒？每秒钟能处理多少比赛？
  • 没有瓶颈分析——DSL 求值是 CPU 密集型还是 IO 密集型？规则加载是瓶颈吗？
  • 没有 Worker 扩容策略——基于什么指标（队列深度、分析延迟、CPU 使用率）进行水平扩缩容？
  • 没有内存预算——每场比赛分析加载多少规则？规则缓存占多少内存？
  • 没有数据库连接估算——N 个检索 Worker × 每个 Worker 的并发连接数 = 总连接数，超过 PostgreSQL 默认值怎么办？
G7
中 P2

配置管理架构缺失

文档中出现了各种常量（BACKTEST_CONFIG、租约 30 秒、心跳 10 秒），但这些配置的管理方式未定义。

  • 没有环境配置分层——开发/测试/生产环境的配置如何管理？
  • 没有动态配置机制——运行时修改租约超时、Worker 池大小等参数是否需要重启？
  • 没有 Feature Flag 机制——新规则匹配算法是否可以灰度发布？
  • 没有配置的版本化与审计——配置变更是否可以追溯？
G8
中 P2

灾备与连续性缺失

Docker Compose 部署拓扑定义了服务，但系统崩溃后的恢复策略未定义。

  • 没有备份策略——PostgreSQL 的备份频率、保留策略、恢复验证流程
  • 没有 RPO/RTO 定义——数据最多丢失多少？系统多久恢复？
  • 没有数据复制策略——是否需要 PostgreSQL Streaming Replication？Redis 是否需要 Sentinel 或 Cluster？
  • 没有多区域部署方案——如果主区域不可用，是否有备用区域？
G9
严重 P0

DSL 语法定义不完整

文档展示了条件求值器的 evaluateCondition 函数，但 DSL 的完整文法未定义。这是整个检索引擎的核心，也是最大的设计空白。

  • 没有完整的 BNF 或 EBNF 文法——规则以什么格式编写？JSON？YAML？自定义 DSL 语法？
  • 没有 Atomic 条件的完整算子集——支持哪些比较？gt、lt、eq、between、in、pattern_match？
  • 没有模糊匹配的定义——fuzzy_matches 在接口中出现了，但匹配算法（Levenshtein？Jaccard？Embedding similarity？）未定义
  • 没有时间条件语法——timeWindow: "临场前30分钟" 这种自然语言如何映射为 DSL 的时间算子？
  • 没有外部数据引用机制——规则如何引用比赛特征（MatchFeatures）中的字段？字段可扩展性如何？
  • 没有条件权重机制——一个 AND 组合中的子条件是否可以有不同权重？
G10
高 P0

融合决策层未定义

图6 的 DSL 引擎架构中出现了"融合决策层"（Result[融合决策层]），但全文没有任何关于这个层的说明。

  • 融合决策的输入是什么？——多条规则匹配结果、冲突组、推理链？
  • 融合决策的策略是什么？——加权投票？置信度排序？贝叶斯融合？
  • 预测方向（PredictionDirection）的枚举值是什么？——favor_upper、favor_lower、under、over、neutral... 这些值如何映射到最终预测？
  • 置信度（final_confidence）的计算公式是什么？——规则置信度的加权平均？最大值？
  • 融合决策层是否支持可配置策略？——不同用户或场景可能需要不同的决策策略
G11
高 P0

冲突仲裁策略不明确

AnalysisResult 接口中有 conflicts: ConflictGroup[]，冲突仲裁器（CM[冲突仲裁器]）出现在架构图中，但仲裁策略完全未定义。

  • 什么算冲突？——规则 A 说"上盘"，规则 B 说"下盘"，这是冲突。但"上盘"和"谨慎"算冲突吗？
  • 仲裁策略是什么？——置信度优先？权威性优先？最近更新优先？
  • 冲突时是否保留所有推理路径？——用于人工审计和回溯
  • 是否允许人工标记冲突？——专家可以手动标记规则之间的冲突，系统在检测到已知冲突时立即告警
  • 冲突组（ConflictGroup）的结构是什么？——参与的规则、冲突类型、建议的仲裁结果
G12
严重 P0

缺失数据模型定义

文档中定义了 qd_analysis_commands 和 qd_evidence_snapshots 两张表，但引用了多张未定义的表。

  • qd_rule_versions 未定义——规则版本的数据模型是什么？rule_id、version、dsl_body、status、author、approved_by？
  • qd_backtest_jobs 未定义——回测作业包含哪些字段？rule_id、config（JSONB）、date_range、result？
  • qd_worker_heartbeats 未定义——心跳记录的结构？worker_id、process_type、last_heartbeat_at、load？
  • qd_analysis_leases 在图2 的说明中被提及，但表结构未定义
  • 没有规则的 DSL 存储格式——规则条件以 JSONB 存储？还是以自定义 DSL 文本存储？
  • 没有索引策略——除了 idx_analysis_pending 和 idx_analysis_expired，其他查询路径缺少索引
G13
高 P0

时间泄漏防护机制不完善

用户背景信息中强调"时间泄漏"是核心约束，但前序设计对时间泄漏防护的描述不够具体，不足以指导实现。

  • observed_at、received_at、match_time 三个时间戳的比较规则是什么？——observed_at ≤ received_at ≤ match_time？
  • analysis_time 的角色是什么？——分析时间应与模拟的历史时间点一致，而不是当前系统时间
  • 回测中的时间泄漏防护——回测时加载历史数据，必须确保分析时只使用"当时"可用的信息
  • TemporalContext 的结构未定义——它包含 analysisTime、eligibleDataWindow、forbiddenFutureData？
  • 时间校验失败时的行为——是跳过分析？标记为不可信？还是记录警告但继续？
  • 反盲区（Look-Ahead Bias）防护——在批量回测时，如何确保第 N 场比赛的分析不会用到第 N+1 场比赛的数据？
G14
中 P1

缓存策略未定义

图6 中规则缓存（R[规则缓存
Redis]）是 DSL 引擎的核心数据源，但缓存策略完全未定义。

  • 缓存失效策略——当规则从 active 变为 deprecated 时，缓存如何失效？
  • 缓存预热——系统启动时，如何将活跃规则加载到缓存？
  • 缓存一致性——如果多个检索 Worker 各自缓存了规则，如何确保缓存一致性？
  • 缓存淘汰策略——Redis 使用 allkeys-lru 还是 volatile-ttl？
  • 分析结果缓存——是否缓存相同比赛的分析结果？如果比赛特征不变，重复分析是否可以返回缓存？
G15
中 P2

幂等键生命周期管理缺失

幂等键通过唯一约束防止重复，但幂等键何时失效？

  • 幂等键的保留期限——分析完成后的幂等键是否永远保留？如果保留，qd_analysis_commands 表会无限增长
  • 幂等键的清理策略——基于时间（完成 30 天后清理）还是基于容量（表大小超阈值后清理最旧的）？
  • 幂等键过期后的行为——如果用户用相同的 requestId 发起新请求，但旧的幂等键已被清理，结果是重复分析还是新分析？
  • 建议：幂等键保留期 = 7 天，超过后允许重新提交。但需记录幂等键的清理审计日志
G16
低 P2

优雅关闭流程缺失

当检索 Worker 接收到 SIGTERM（如 Kubernetes 滚动更新、Docker Compose down），当前正在执行的分析任务怎么办？

  • 没有优雅关闭的步骤定义——收到 SIGTERM → 停止认领新任务 → 完成当前任务 → 释放租约 → 退出
  • 没有超时机制——SIGTERM 后最多等待多少秒？超时后强制 SIGKILL？
  • 没有 PreStop Hook——Kubernetes 中应配置 preStop 通知 Worker 即将关闭
  • 没有孤儿任务处理——如果 Worker 被强制杀死，租约在 30 秒后自动过期，其他 Worker 可以认领
G17
中 P1

指标定义缺失

健康检查端点返回了 Workers 数量，但系统需要更丰富的指标来驱动运维决策和业务分析。

  • 业务指标缺失——规则命中率（kb_rule_hit_rate）、预测准确率（kb_prediction_accuracy）、规则覆盖率（kb_rule_coverage）
  • 系统指标缺失——分析队列深度（kb_analysis_queue_depth）、租约过期率（kb_lease_expiry_rate）、分析延迟 P50/P95/P99（kb_analysis_latency_ms）
  • Worker 指标缺失——Worker 任务完成率（kb_worker_task_completion_rate）、Worker 崩溃率（kb_worker_crash_rate）
  • 缓存指标缺失——缓存命中率（kb_cache_hit_ratio）、缓存大小（kb_cache_size_bytes）
  • 建议：为每个指标定义名称、类型、标签（worker_id、process_type）、采样间隔
G18
高 P0

外部数据源集成策略缺失

知识库需要从外部获取比赛数据（赔率、比分、球队信息等），但架构文档没有定义数据集成的方式。

  • 没有数据源接入规范——外部数据源（机构赔率 API、联赛数据提供商）如何接入？
  • 没有数据管道——数据采集、清洗、转换、加载的 ETL/ELT 流程未定义
  • 没有数据源的健康检查——如果赔率数据源不可用，系统是降级还是拒绝服务？
  • 没有数据质量评级——不同数据源的数据质量不同，是否应该有数据源的可信度评级？
  • 没有增量更新策略——比赛数据是实时推送还是定时拉取？增量更新还是全量替换？
G19
高 P0

跨域依赖时序问题未解决

图1 的并发域依赖关系图中，回测作业完成后会"更新规则置信度"，这触发规则生命周期的状态重新评估。但时序问题未定义。

  • 回测更新置信度时，如果规则正在被检索 Worker 使用，是否会影响正在进行的分析？
  • 置信度更新是同步还是异步？——如果同步，调度 Worker 可能阻塞等待规则状态转换锁
  • 活跃规则的热更新——当规则置信度变化时，正在运行的 DSL 匹配是否应该使用新置信度？
  • 建议：规则置信度更新采用"写时复制"模式——更新只影响新分析任务，不影响正在进行的分析
  • 建议：定义跨域依赖的时序图，明确每个操作的顺序和一致性要求
G20
中 P2

规则版本对比与回滚缺失

规则版本状态机（图5）定义了 superseded 状态，但版本对比和回滚机制未定义。

  • 没有版本对比工具——如何比较两个版本规则的 DSL 差异？
  • 没有回滚机制——如果新版本发布后预测准确率下降，如何快速回滚到旧版本？
  • 没有 A/B 测试框架——新旧版本是否可以同时运行，用实际数据验证？
  • 没有统一的语义化版本标签和发布约束
  • 没有版本发布说明——每个版本变更的 changelog 机制

总结与路线图

前序架构在并发安全、进程隔离、幂等性这三个维度上，方向完全正确。但架构设计文档的实际覆盖范围远小于一个可交付系统所需的完整设计。以下是按优先级排序的补齐路线图建议：
