1. 设计目标与指标

1.1 设计目标

本系统为个人研究项目（1-10 用户），负载远低于生产级系统。性能模型的目标不是支撑大规模并发，而是：

  1. 明确量化指标，指导部署决策（Worker 数、内存、DB 连接）
  2. 识别瓶颈，避免过度设计（不需要为百万 QPS 设计）
  3. 建立基准测试基线，验证后续优化效果
  4. 预留合理的扩展空间（规则数增长、数据积累）

1.2 核心指标目标

指标目标告警阈值来源
分析提交延迟（API 202 响应）P95 < 100ms> 300ms本设计
分析完成延迟（提交→完成）P95 < 3000ms> 3000ms（P2）retrieval-engine
规则查询延迟P95 < 50ms> 150ms本设计
缓存命中率≥ 0.5< 0.5（P3）retrieval-engine
单场分析吞吐≥ 5 场/秒/Worker< 2 场/秒本设计
回测作业（1000 场）≤ 5 分钟> 10 分钟本设计

2. 负载模型

2.1 用户与请求规模

维度规模说明
用户数1-10个人研究 + 少量协作者
比赛规模300-400 场/周主流联赛（日职/英超/德甲/西甲/意甲/法甲等）
分析请求高峰 300 场/小时开赛前 1 小时集中提交
规则规模16 → 100 条当前 16 条，扩展至 100 条预留
历史数据1-3 年约 1.5-5 万场

2.2 请求模式

// 高峰时段（开赛前 1 小时）
峰值请求率 = 300 场 / 3600 秒 ≈ 0.08 场/秒

// 对比系统容量（见第 3 节）
系统容量 = 2 Worker × 5 场/秒 = 10 场/秒

// 容量余量
余量 = 10 / 0.08 ≈ 125 倍
结论

负载远低于容量，系统设计以正确性、可追溯性、可维护性为优先，性能不是瓶颈。但仍需建立基准测试基线，防止规则数增长或数据积累后出现性能退化。

5. 瓶颈分析

环节类型是否瓶颈分析
DSL 求值CPU 密集否（当前）500 次原子求值 ≈ 150ms。规则数 ×10（1000 条）后约 1.5s，接近预算上限，需关注
规则加载内存否启动时全量加载，运行时零 DB 访问
特征计算IO 密集否缓存命中 10-30ms；未命中需从盘口快照计算（+50ms）
证据写入IO（PG）否append-only INSERT，单条 10-20ms
模糊匹配CPU否加权 Jaccard，仅触发规则使用，量小
回测全量扫描CPU + IO潜在5 万场 × 单场求值，需控制并发与队列优先级
规则数增长预警

DSL 求值是主要 CPU 消耗。当 active 规则数达到 1000 条时，单场求值约 1.5s，接近 3000ms 预算的 50%。届时可引入：条件索引（按字段预筛）、规则分组并行求值、或求值结果缓存。当前 100 条规模无需优化。

7. 缓存策略

缓存项存储TTL失效策略命中率目标
规则缓存（active）进程内存常驻规则状态变更时重建（事件驱动）100%
特征缓存Redis30 分钟开赛前特征变化频繁，短 TTL≥ 0.7
比赛数据缓存Redis1 小时盘口快照更新时失效≥ 0.8
分析结果缓存Redis24 小时同场重复分析直接返回≥ 0.5
字段注册表进程内存常驻注册表变更时重建100%
 
// 缓存键设计
rule:active            // 全量 active 规则（Hash）
feature:{match_id}     // 单场特征
match:{match_id}       // 比赛 + 盘口快照
analysis:{command_id} // 分析结果
idem:{key}            // 幂等键（24h）
rl:{scope}:{user_id} // 限流计数
jwt:{jti}            // JWT 黑名单
缓存一致性

规则缓存采用事件驱动失效：规则状态转换（INSERT 新版本）后发布事件，Worker 监听并重建缓存。特征缓存采用 TTL + 主动失效双机制，保证 point-in-time 语义不被缓存破坏。

8. 队列模型

8.1 队列优先级

队列优先级并发说明
实时分析高8用户等待结果，优先处理
回测作业低4后台任务，不阻塞实时分析
数据同步低2数据源拉取

8.2 队列深度估算

// 高峰场景：开赛前 1 小时集中提交 300 场
入队速率 = 300 / 3600 ≈ 0.08 场/秒
处理速率 = 2 Worker × 6.7 场/秒 ≈ 13 场/秒

// 稳态队列深度 ≈ 0（处理速率 >> 入队速率）
// 最坏情况：300 场瞬间入队
最大队列深度 = 300
清空时间 = 300 / 13 ≈ 23 秒  // 远低于延迟预算

9. 扩容策略

9.1 扩容触发条件

指标扩容条件操作
队列深度> 100 持续 5 分钟增加 1 个检索 Worker
分析延迟 P95> 3000ms 持续 5 分钟增加 1 个检索 Worker
CPU 使用率> 70% 持续 10 分钟增加 1 个 Worker

9.2 缩容触发条件

指标缩容条件操作
队列深度< 10 持续 30 分钟减少 1 个 Worker（最小 1）
CPU 使用率< 20% 持续 1 小时减少 1 个 Worker（最小 1）
当前规模说明

当前负载（0.6% 利用率）下无需自动扩缩容，固定 2 个检索 Worker 即可。扩容策略为数据量 / 规则数增长后预留，通过 Prometheus 指标驱动。
