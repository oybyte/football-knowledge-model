API 契约 1.0.0

G1 — OpenAPI 3.0 接口规范 + G4 — 安全与权限设计
版本: 1.0.0 日期: 2026-08-18 状态: 设计 前置: data-model-1.0.0 / dsl-syntax-1.0.0 / retrieval-engine-1.0.0 覆盖缺口: G1, G4

1. 设计原则

  1. 资源为中心：URL 路径以资源命名，操作通过 HTTP 方法表达。
  2. 幂等性：POST 创建类接口支持幂等键（Idempotency-Key 头），重放不产生重复资源。
  3. 版本化：URL 路径前缀 /api/v1，大版本更新时升级路径版本。
  4. 无状态：认证通过 JWT Bearer Token 传递，服务端不维护会话。
  5. 一致错误格式：所有错误响应遵循 RFC 9457 Problem Details 规范。
  6. 最小权限：每个接口按 RBAC 权限矩阵控制访问，默认拒绝。
  7. 可追溯：关键操作记录审计日志，通过 X-Request-Id 关联。

3. 认证与授权

3.1 认证流程

// POST /api/v1/auth/login — 登录获取 JWT
Request:
{
  "username": "analyst01",
  "password": "..."       // 通过 TLS 1.3 传输
}

Response 200:
{
  "data": {
    "access_token": "eyJhbGciOi...",
    "token_type": "Bearer",
    "expires_in": 3600,           // 1 小时过期
    "refresh_token": "...",
    "role": "analyst"
  }
}

// POST /api/v1/auth/refresh — 刷新令牌
Request:
{
  "refresh_token": "..."
}

// POST /api/v1/auth/api-token — 创建 API Token（长期有效，Admin 操作）
Request:
{
  "label": "ci-cd-deploy",
  "role": "viewer",
  "expires_in_days": 90
}

3.2 JWT 载荷结构

{
  "sub": "user_abc123",           // 用户 / 系统 ID
  "role": "analyst",             // viewer | analyst | reviewer | admin
  "iat": 1712345678,
  "exp": 1712349278,
  "jti": "unique-token-id",      // 用于吊销
  "type": "user"                   // user | api_token | service
}

3.3 角色中间件

每个接口通过角色中间件校验 JWT 中的 role 字段，未授权返回 403。中间件链：

Request → AuthMiddleware (验证 JWT 签名 / 过期 / 吊销) 
           → RoleMiddleware (校验角色 ≥ 所需等级)
           → RateLimitMiddleware (滑动窗口限流)
           → AuditMiddleware (关键操作写入审计日志)
           → Handler

3.4 吊销与黑名单

JWT 签发时存入 Redis（key: jwt:{jti}，TTL 与 token 过期时间一致）。管理员可将 jti 加入黑名单（Redis key: jwt:blacklist:{jti}），AuthMiddleware 在校验时检查黑名单。

4. 错误处理

4.1 HTTP 状态码体系

状态码场景说明
200成功GET / PUT / PATCH 操作成功
201创建成功POST 资源创建成功，响应含 Location 头
202已接受异步操作（分析请求、回测作业）提交成功
204无内容DELETE 操作成功
400请求参数错误参数格式 / 必填字段缺失
401未认证缺少 Authorization 头或令牌无效
403权限不足角色不满足接口要求
404资源不存在指定 ID 的资源未找到
409冲突幂等键重复且请求内容不一致、状态转换非法
422校验失败DSL 编译校验失败、字段值域越界等
429请求过频速率限制触发，响应含 Retry-After 头
500服务端错误未预期异常
503服务不可用Redis / PG 不可用，队列满

4.2 DSL 错误码映射

DSL 编译期与运行期错误码映射到 HTTP 422 响应：

DSL 错误码含义HTTP 状态错误类型 URI
E1001未知字段422/errors/validation-error
E1002类型不匹配422/errors/validation-error
E1003值域越界422/errors/validation-error
E1004非法正则422/errors/validation-error
E2001时间泄漏200（告警）/errors/time-leakage-warning
E2002字段缺失200（告警）/errors/field-missing-warning

5. 规则 API

GET /rules Viewer

获取规则列表，支持按状态 / 分类 / 联赛筛选。

Query: status (active|draft|...), category, league, page, page_size

Response 200: 规则列表，每项含 rule_id, name, category, status, current_version, evidence_count

POST /rules Analyst

创建规则（draft 状态）。

Request: rule_id, category, condition (DSL JSON), direction, base_confidence, priority

Response 201: version_id, version, status: "draft"

422: DSL 编译校验失败，含错误码 E1001-E1004

GET /rules/{rule_id} Viewer

获取规则详情（最新版本）。

Response 200: 规则完整信息，含 condition DSL 表达式

GET /rules/{rule_id}/versions Viewer

获取规则版本历史。

Response 200: 版本列表，每项含 version, status, created_at, created_by

GET /rules/{rule_id}/versions/{version} Viewer

获取指定版本的规则详情。

PUT /rules/{rule_id}/versions/{version} Analyst

更新规则 （仅当版本处于 draft 状态）。更新实质为 INSERT 新版本（version+1），旧版本标 superseded。

Request: 同创建规则，condition 等可修改字段

Response 201: 新版本 ID，version 递增

POST /rules/{rule_id}/versions/{version}/transition 按角色

规则状态转换。

Request: target_status (proposed|experiment|validated|approved|active|deprecated)

Response 200: 新状态，新版本记录（INSERT version+1）

409: 非法状态转换（如 draft→approved 直接跳转）

角色要求:

  • draft→proposed: Analyst
  • proposed→experiment: Reviewer
  • experiment→validated: 自动（回测达标）
  • validated→approved: Admin
  • approved→active: Admin
  • active→deprecated: Reviewer
GET /rules/{rule_id}/versions/{version}/compare Viewer

版本对比。

Query: to (对比目标版本号)

Response 200: 两个版本的 diff 结果（DSL 条件差异）

POST /rules/{rule_id}/rollback Admin

回滚到指定版本（INSERT 新版本，内容和目标版本一致）。

Request: target_version

Response 201: 新版本 ID

GET /rules/{rule_id}/evidence Analyst

获取规则关联的证据快照列表。

Query: eligible (boolean), page, page_size

GET /rules/{rule_id}/backtest-jobs Analyst

获取规则的回测作业历史。

11.3 凭证隔离（CredentialVault）

遵循架构工程契约——AI 模块无数据源凭证访问权限：

  • 数据源凭证：存于环境变量或 Vault，通过 config_ref 引用，不落库
  • 系统凭证（PG / Redis）：存于环境变量，仅 API 进程启动时读取
  • AI 模型凭证（API Key）：存于环境变量，AI 引擎模块可读，但不可读取数据源凭证
  • 凭证访问审计：所有凭证读取操作记录到 qd_audit_log（event_type: credential_accessed）

14. 幂等键规范

  • 覆盖接口：POST 创建类接口（规则创建、分析请求、回测作业、AI 挖掘）
  • 传递方式：HTTP 头 Idempotency-Key: {uuid-v4}
  • 有效期：24 小时，过期后允许复用
  • 行为：
    • 首次请求 → 正常处理，返回 201/202
    • 相同 key 重放（24h 内）→ 返回首次结果（幂等），不重复创建
    • 相同 key 但请求 Body 不同 → 409 Conflict
  • 存储：Redis key: idem:{key}，值 = {response_body, status_code, created_at, request_body_hash}
  • 请求体哈希：SHA-256(request_body) 用于重放一致性校验
// 幂等键中间件逻辑
async function idempotencyMiddleware(req, res, next) {
  const key = req.headers['idempotency-key'];
  if (!key) { return next(); }

  const existing = await redis.get(`idem:${key}`);
  if (existing) {
    if (existing.body_hash !== sha256(req.body)) {
      return res.status(409).json({ "title": "幂等键冲突" });
    }
    return res.status(existing.status_code).json(existing.response_body);
  }

  // 保存请求记录
  await redis.set(`idem:${key}`, {
    body_hash: sha256(req.body),
    status_code: res.statusCode,
    response_body: res.body,
    created_at: Date.now()
  }, 'EX', 86400);

  next();
}
